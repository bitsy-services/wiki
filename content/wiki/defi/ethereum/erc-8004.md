ERC-8004 is a **Draft** [ERC](https://eips.ethereum.org/EIPS/eip-1) that defines an on-chain trust layer for autonomous AI agents. It provides discovery, identity, and reputation primitives so that agents built on protocols like [MCP](https://modelcontextprotocol.io/) or [A2A](https://google.github.io/A2A/) can interact across organisational boundaries without pre-established trust.

The standard specifies three lightweight singleton registries deployable on any EVM chain.

## Registries

### Identity Registry

Built on [ERC-721](https://eips.ethereum.org/EIPS/eip-721) with URI storage. Each agent is minted as an NFT identified globally by `{namespace}:{chainId}:{identityRegistry}:{agentId}`. The token URI resolves to a **registration file** — hosted on IPFS, HTTPS, or as a base64 data URI — that describes the agent's capabilities, supported protocols, wallet addresses, [DIDs](https://en.wikipedia.org/wiki/Decentralized_identifier), and ENS names.

Key methods:

| Method | Purpose |
|---|---|
| `register()` | Mint a new agent identity NFT |
| `setAgentURI()` | Update the registration file pointer |
| `setAgentWallet()` | Associate an on-chain wallet with the agent |
| `getMetadata()` / `setMetadata()` | Read or write arbitrary key-value metadata |

### Reputation Registry

A standardised interface for posting and reading feedback signals. Feedback is a fixed-point value (`int128` with configurable decimals) and can include tags, endpoint references, and external file URIs with integrity hashes.

Key methods:

| Method | Purpose |
|---|---|
| `giveFeedback()` | Submit a feedback signal for an agent |
| `revokeFeedback()` | Retract previously submitted feedback |
| `appendResponse()` | Allow the agent to respond to feedback |
| `getSummary()` | Aggregate feedback for an agent |
| `readFeedback()` | Read individual feedback entries |

Scoring and aggregation can happen on-chain (for composability with other contracts) or off-chain (for more sophisticated algorithms).

### Validation Registry

Generic hooks for requesting and recording independent verification of agent work. Validators respond on a 0–100 scale, usable as binary pass/fail or as a spectrum. The standard is agnostic about the validation strategy — implementations may use stake-secured re-execution, [zkML](https://en.wikipedia.org/wiki/Zero-knowledge_proof) proofs, [TEE](https://en.wikipedia.org/wiki/Trusted_execution_environment) oracle attestation, or trusted human judges.

Key methods:

| Method | Purpose |
|---|---|
| `validationRequest()` | Request validation of agent work |
| `validationResponse()` | Submit a validation result |
| `getValidationStatus()` | Check whether validation is pending or complete |
| `getSummary()` | Aggregate validation results |

## Design Decisions

- **Agents as NFTs** — immediate compatibility with existing wallets, marketplaces, and tooling.
- **Off-chain registration file** — bridges on-chain identity to multiple communication protocols and identifier systems without bloating contract storage.
- **Protocol-agnostic** — combines [A2A](https://google.github.io/A2A/) nomenclature (tasks, skills) with MCP concepts (tools, prompts) so the standard is not locked to a single agent framework.
- **[EIP-7702](https://eips.ethereum.org/EIPS/eip-7702) friendly** — leverages account abstraction for gas-sponsored feedback transactions, lowering the barrier for clients to submit reputation signals.

## Dependencies

| EIP | Role |
|---|---|
| [EIP-155](https://eips.ethereum.org/EIPS/eip-155) | Chain ID in agent identifiers |
| [EIP-712](https://eips.ethereum.org/EIPS/eip-712) | Typed structured data for off-chain signatures |
| [ERC-721](https://eips.ethereum.org/EIPS/eip-721) | NFT base for the Identity Registry |
| [EIP-1271](https://eips.ethereum.org/EIPS/eip-1271) | Smart-contract signature validation |

## Security Considerations

- **Sybil attacks** — fake agents can inflate reputation through collusion. Mitigated by public signal transparency and client-side reviewer filtering, but not fully solved at the protocol level.
- **Capability honesty** — the standard cannot cryptographically guarantee that an agent performs what it advertises. The three trust models (reputation history, independent validation, TEE attestation) are layered defences.
- **Validator incentives** — slashing and reward mechanics are delegated to specific validation protocol implementations, not prescribed by the ERC itself.
